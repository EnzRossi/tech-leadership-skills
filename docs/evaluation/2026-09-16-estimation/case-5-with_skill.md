**Ten days is an unvalidated hypothesis, not a defensible delivery estimate.** The arithmetic **100 ÷ 10 = 10** is correct only if the vendor's claim applies to the entire accepted delivery workflow. There is no evidence that it does. Faster code generation does not necessarily shorten domain decisions, review, integration, testing or release gates by the same factor.

Use this board wording:

> Delivery timing is unvalidated. The vendor reports a 10× agent speedup, but we have not measured it against our scope or acceptance bar. We will forecast after one representative slice completes implementation, review, fixes, integration and acceptance.

As a proposed engineering-judgment allocation, timebox **1–2 working days** to define scope and acceptance and prepare a representative slice. This is a discovery commitment, not a promise that the slice or project finishes in that period. Include a risky integration rather than selecting only a trivial task.

Measure human framing/steering/review/fix effort separately from unattended agent runtime, and record start-to-accepted elapsed time. Include failed attempts and reruns. Map remaining work and external gates, then compare staffing only where independent work and reviewer capacity support it.

Neither a firm date nor a monetary budget follows from the supplied information. The old 100-day figure remains a historical manual estimate, not an agentic baseline. Removing this uncertainty from the board deck would turn an unsupported vendor claim into an apparent commitment. The sponsor should approve the calibration step and receive a revised forecast at its acceptance boundary.
